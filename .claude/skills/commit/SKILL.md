# Commit

작업 트리의 변경사항을 분석해 컨벤션에 맞게 커밋한다. 사용자의 별도 승인을 기다리지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

- `git status`로 변경된 파일과 untracked 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다.
- `git log --oneline -10`으로 이 저장소의 기존 메시지 스타일을 확인한다.
- git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 멈춘다.
- `.env`, 키, 토큰 등 비밀 정보가 포함돼 있으면 커밋 대상에서 빼고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 한 파일 안에서 목적이 다른 변경이 섞여 있으면 하나의 커밋으로 묶고, 완료 보고에 그 사실을 적는다.
- 각 단위에 포함할 파일 목록을 정리한다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

type은 아래 중 하나를 쓴다.

| type | 용도 |
| --- | --- |
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 빌드, 설정, 의존성, 문서 등 기타 작업 |

규칙:

- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 마침표는 붙이지 않는다.
- "무엇을 했는지"보다 "왜, 어떤 효과가 있는지"가 드러나게 쓴다.
- 본문은 요약만으로 부족할 때만 쓴다. 한 줄 띄우고 이유와 영향을 적는다.
- 기존 로그가 다른 스타일이면 type 목록은 유지하되 그 저장소의 어조에 맞춘다.
- 마지막 줄에 위 `Co-Authored-By` 줄을 항상 붙인다.

### 4. 바로 커밋

- 승인을 묻지 않고 커밋 단위마다 해당 파일만 `git add <파일>`로 스테이징하고 커밋한다. `git add -A`와 `git add .`는 쓰지 않는다.
- 메시지는 여러 줄이므로 heredoc으로 `git commit -m`에 전달한다.
- 모두 끝나면 `git log --oneline`으로 만든 커밋 목록과 각 커밋에 포함된 파일을 보고한다.

## 하지 않는 일

- `git push`는 사용자가 따로 요청할 때만 한다.
- `--no-verify`나 `--amend`는 사용자가 명시적으로 요청하지 않으면 쓰지 않는다. pre-commit 훅이 실패하면 원인을 고치고 새 커밋을 만든다.
