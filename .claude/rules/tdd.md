# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "정신만 따르는" 식으로 완화하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (엔드포인트, 핸들러, 응답 정규화)
- **유틸 / 순수 함수**
- **버그 수정** — 버그를 재현하는 실패 테스트를 먼저 작성한다

### TDD 불필요

- 타입 정의 (`type`, `interface`)
- 설정 파일 (`vite.config.ts`, `tsconfig`, `.eslintrc` 등)
- 순수 UI (로직 없는 마크업/스타일)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **TDD를 적용한다.**

## 2. RED-GREEN-REFACTOR

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행 없이 "실패할 것"이라고 가정하지 않는다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니다 — 고치고 다시 실행한다.

### GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트 + 기존 테스트 모두 통과**를 실행으로 확인한다.

### REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green 상태를 유지**한다. 수정할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대해 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. **RED부터 재시작**한다.

- "참고용"으로 남기는 것도 **금지**다. 주석 처리, 별도 파일 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다.
- 삭제한 코드를 기억에 의존해 그대로 재현하지 말고, 테스트가 요구하는 것만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 끝난다. 단순한 코드가 가장 자주 깨지고, 테스트가 이후 변경의 안전망이 된다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 **항상 통과**한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. TDD는 속도를 늦추는 게 아니라 재작업을 줄인다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. 삭제 후 재작성은 빠르다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 삭제가 아깝지도 않다. 남길 코드라면 테스트가 필요하다. |

## 체크리스트

- [ ] 대상이 TDD 필수 범주인가?
- [ ] 테스트를 **실행해서** 기능 미구현으로 실패하는 것을 봤는가?
- [ ] 최소 코드만 작성했는가?
- [ ] 신규 + 기존 테스트가 모두 통과하는가?
- [ ] 리팩터링 중 새 동작을 추가하지 않았는가?
